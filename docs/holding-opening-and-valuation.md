# 已有持仓、历史买入与官方计价

版本：`2026.11.03-holding-opening`。本次包含此前新增的删除流水功能。

## 录入已有持仓

持仓 → 录入已有持仓，或「记一笔」后切换至「录入已有持仓」。

支持两种方式：

1. **持有份额 + 剩余成本**：按平台上的实际份额、尚未退出的成本登记；登记日期不冒充原始买入日期。
2. **持仓市值 + 持有盈亏**：两者须对应同一官方净值日。成本 = 市值 − 持有盈亏，份额 = 市值 ÷ 该日官方净值，份额保留 6 位。持有盈亏不含已卖出收益、现金分红；缺少该日官方净值时拒绝换算并保留输入，可改用份额录入。

已有持仓保存为 `entry_type=opening`，同时原子写入一条期初登记活动，不伪造新的买入。持仓来源保存在持仓自身的新字段中，删除历史活动或后续校正不会丢失这个身份。

每次录入和每行导入都会**新增**持仓，不自动覆盖已有记录。已记录过同一批份额时应校正现有持仓，不要再次录入；只删除流水不会删除当前持仓。

## 导入

导入与对账分为「导入已有持仓」「导入买入记录」，已有持仓再选择份额/成本或市值/盈亏模板。支持 CSV 引号、逗号备注、制表符；超出 20 行明确报错，不静默截断后提交。

已有持仓模板分别为：

```csv
基金代码,持有份额,剩余成本,登记日期,备注
014662,500,900,2026-11-02,示例数据
```

```csv
基金代码,持仓市值,持有盈亏,净值日期,备注
014662,1000,100,2026-11-02,示例数据
```

历史买入保留原交易时间；仅填日期时，使用导入面板明确选择的默认 15:00 前/后规则。带入买入表单也保留时间，不再重置到今天。部分成功时，本次预览只重试失败行；刷新页面后应自行核对已有数据，避免再次导入已完成行。

## 计价修复

- 中国基金净值的 Unix 时间戳统一按 Asia/Shanghai 转成日期，避免 UTC 服务器提前一天。
- 使用最新**可用且合法**的已公布官方净值，明确显示实际净值日和待更新状态；当天尚未公布时不再把所有市值清空，也不偷偷切到盘中预估。
- 未确认买入不能使用早于其确认日的净值。旧买入缺少确认数据时按需获取相应历史日期，不再只依赖夜间最近 30 条窗口。
- 源请求去重、限制并发和缓存；普通列表读取不会等待外部网络。待确认/待更新持仓会自动轮询，数据到齐后回填。
- 修复窗口依据官方源最近最多 30 条、且不超过 90 日的区间重建，清理该窗口的错位日期；请求的更早确认日单独补齐，不删除其他历史范围。
- 份额回填使用条件更新，不能覆盖同时发生的人工校正。期初、人工份额和不再符合原自动推算关系的再投/调整份额保持原值。

如果旧记录本身把当前市值误填成买入成本，系统无法从旧金额自动推断真实份额和成本，需要按平台实际数据校正。

## 发布顺序（现有数据库）

1. 备份 FundLive 数据库；本次不重建数据库，不重跑空库文件。
2. 先执行 `scripts/sql/upgrade-20261103-holding-opening.sql`，仅增加 `tb_user_fund_holding.entry_type` 并记录迁移 ID。
3. 更新后端，再重新构建/发布前端。健康检查版本应为 `2026.11.03-holding-opening`。

Docker 数据库的示例命令（在服务器解包目录执行）：

```bash
infra-compose exec -T postgres psql -U postgres -d fundlive -v ON_ERROR_STOP=1 \
  < upgrade-20261103-holding-opening.sql
```

新数据库仍使用重新导出的 `fundlive-schema.sql`。已有期初数据后，应使用理解 `entry_type` 的 API 版本；回退到更早的买入-only 程序可能误解这些记录。

后端包仍为 `target/fund-live-backend-linux-amd64.tar.gz`，包含 API、crawler、校验和、完整空库 SQL 和独立升级 SQL。前端本地 fixture 构建仅用于验证，不直接作为生产产物部署。
